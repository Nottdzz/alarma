# Especificación de Requerimientos de Software (SRS)

**Proyecto:** Sistema de Gestión de Horarios, Alarmas y Estado Emocional Escolar  
**Versión:** 1.0.0  
**Stack Tecnológico Target:** HTML5, CSS3, JavaScript (Vanilla ES6+), Node.js (Express), SQLite3  

---

## 1. Introducción y Propósito

El propósito de este documento es definir las especificaciones funcionales y no funcionales para la aplicación de gestión de tiempo orientada a estudiantes escolares[cite: 5]. El sistema centraliza la organización de horarios semanales y específicos[cite: 1, 3], la programación de alarmas con ejecución secuencial en caso de superposición[cite: 1, 4], y la gestión de notas informativas junto con el registro del estado emocional diario del usuario[cite: 5, 6].

---

## 2. Definición de Requerimientos (Matriz MoSCoW)

### 2.1. Must Have (Obligatorio)
* **RF-01:** El sistema debe permitir el registro, autenticación e inicio de sesión de usuarios (escolares) para asociar de manera privada la información de cada cuenta[cite: 1].
* **RF-02:** El sistema debe gestionar el CRUD completo (Crear, Leer, Actualizar y Eliminar) de los horarios según el día y la hora definidos por el usuario[cite: 1, 2, 3].
* **RF-03:** El sistema debe permitir programar, editar y eliminar alarmas asociadas a las actividades del horario o de manera independiente[cite: 1, 2, 4].
* **RF-04:** El sistema debe implementar un mecanismo de colas para la ejecución secuencial de alarmas cuando existan eventos que coincidan en la misma hora (sonar la primera alarma y, al ser atendida, disparar la siguiente)[cite: 2, 4].
* **RF-05:** Persistencia de todos los datos en una base de datos relacional SQLite vinculada al identificador del usuario[cite: 1].

### 2.2. Should Have (Debería tener)
* **RF-06:** El sistema debe permitir asignar un título y una descripción personalizada a cada actividad registrada[cite: 3, 6].
* **RF-07:** El sistema debe permitir activar o desactivar las alarmas de forma individual mediante un conmutador (toggle) sin necesidad de eliminarlas[cite: 4, 6].
* **RF-08:** Interfaz visual para la consulta de la agenda escolar organizando los bloques por días de la semana[cite: 1, 2, 7].

### 2.3. Could Have (Podría tener)
* **RF-09:** El sistema debe incluir un módulo para el registro del estado emocional del estudiante durante los días de la semana[cite: 6].
* **RF-10:** El sistema debe permitir la creación de notas rápidas y recordatorios adicionales de apoyo[cite: 5, 6].

### 2.4. Won't Have (No tendrá en esta versión)
* **RF-11:** Sincronización bidireccional automática con aplicaciones externas como Google Calendar, Microsoft To Do, Todoist o Apple Calendar[cite: 7].
* **RF-12:** Envío de notificaciones Push fuera del entorno web local cuando el navegador esté completamente cerrado.

## 4. Casos de Uso Principales

### UC-01: Registro y Gestión de Horarios
* **Actor Principal:** Usuario (Escolar)[cite: 5].
* **Precondición:** El usuario debe haber iniciado sesión en la aplicación[cite: 1].
* **Flujo Principal:**
  1. El usuario selecciona la opción "Agregar Actividad" en la interfaz[cite: 2, 7].
  2. El sistema despliega un formulario solicitando: Día/Fecha, Hora Inicio, Hora Fin y Título de la actividad[cite: 3, 6].
  3. El usuario completa los datos y envía el formulario[cite: 3].
  4. El Frontend envía una petición HTTP `POST` a la API (`/api/horarios`)[cite: 2, 3, 7].
  5. El Backend en Node.js procesa la solicitud, asigna el `usuario_id` y guarda el registro en SQLite[cite: 1, 3, 7].
  6. El Backend responde con un código `201 Created` y el Frontend actualiza el horario en pantalla[cite: 2, 3, 7].
* **Flujos Alternativos:**
  * **4a. Datos incompletos o formato inválido:** El Backend responde con código `400 Bad Request`[cite: 2, 3] y el Frontend le indica al usuario los campos que debe corregir.

---

### UC-02: Disparo de Alarmas en Secuencia
* **Actor Principal:** Sistema / Usuario[cite: 7].
* **Precondición:** Existen alarmas configuradas y activas para la hora actual[cite: 4, 7].
* **Flujo Principal:**
  1. El cliente web (JavaScript) verifica periódicamente el reloj local frente a las alarmas activas cargadas[cite: 4, 7].
  2. Si coinciden dos o más alarmas a la misma hora, el sistema las ordena en una **Cola de Reproducción**.
  3. El sistema ejecuta el sonido de la primera alarma y muestra una ventana en pantalla con el mensaje correspondiente[cite: 4].
  4. El usuario interactúa con la alerta presionando "Aceptar" o "Desactivar"[cite: 4, 6].
  5. El sistema da por finalizada la alarma actual e inicia inmediatamente la reproducción de la siguiente alarma presente en la cola.

## 5. Requerimientos No Funcionales (RNF)

* **RNF-01 (Rendimiento):** El servidor Express en Node.js debe responder a las consultas de horarios y alarmas (`GET`) en un tiempo no mayor a 200 ms.
* **RNF-02 (Interfaz de Usuario):** La interfaz construida con HTML y CSS debe ser adaptable a pantallas de computadoras portátiles, tablets y teléfonos móviles (Diseño Responsive).
* **RNF-03 (Compatibilidad Web):** La aplicación debe funcionar correctamente en navegadores basados en Chromium (Google Chrome, Microsoft Edge, Brave) y Mozilla Firefox haciendo uso de las APIs estándar del navegador.
* **RNF-04 (Seguridad):** Las contraseñas registradas en la base de datos SQLite no deben guardarse en texto plano; deben encriptarse mediante hash (ej. `bcrypt`) antes de su almacenamiento.
